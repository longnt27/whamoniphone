# Final Repository and Report Design

## Purpose

Turn the current research workspace into a readable, reproducible project that
contains one clearly identified mobile pipeline, the evidence used to select
it, a physical-device workload measurement, and an honest account of the
failed approaches that led to it.

The refactor must preserve the validated runtime behavior:

`YOLO26m-pose → HMR2.0-S → selected residual token adapter → WHAM_I →`
`causal WHAM_ImageStep → light output smoothing → WHAM_WorldStep`.

## Repository structure

The top level will contain only the product, its documentation, reproducible
evaluation, current tooling, and a clearly labelled historical archive:

```text
WhamApp/                 iOS application and tests
docs/                    final report and design/implementation records
evaluation/
  results/               immutable selected accuracy and device evidence
  methodology/           concise protocol notes
tools/
  export/                current Core ML exporters
  evaluation/            current grid and smoothing evaluators
  kaggle/                notebooks needed to reproduce selected results
archive/experiments/     superseded FastViT, BEDLAM, and earlier comparison work
README.md                build, run, reproduce, and result summary
```

Generated caches, Repomix outputs, downloaded model weights, Core ML build
products, and other recoverable local artifacts will not be part of the source
tree. Superseded research source will be archived rather than destroyed.

## iOS architecture

The current implementation is correct but repeats preprocessing and recurrent
state logic across `WhamAnalyzer.swift` and `WhamBenchmark.swift`. The refactor
will introduce small shared units:

- `MobileWhamModelCatalog.swift`: canonical model names and provenance.
- `MobileWhamTypes.swift`: observations, HMR output, and recurrent/world state.
- `MobileWhamPreprocessor.swift`: person crop, keypoint normalization, masks,
  and pixel-buffer conversion.
- `MobileWhamCore.swift`: first-frame HMR2-S/SMPL initialization and one causal
  WHAM/world step, including output-only smoothing.
- `WhamAnalyzer.swift`: video decoding, gyro lookup, two-phase memory strategy,
  result serialization, and progress reporting.
- `WhamBenchmark.swift`: fixed sample orchestration, timing collection,
  connectivity guards, device metadata, and JSON persistence.

The analyzer may continue unloading vision models before loading recurrent
models to control memory. Shared types and operations must not force every
model to remain resident simultaneously. The benchmark will keep all selected
models loaded because it intentionally measures the complete workload and peak
resident memory.

No metric, model, threshold, tensor dtype, crop geometry, recurrent feedback,
or smoothing placement may change during this refactor.

## Evidence model

The repository will keep canonical copies of:

- the YOLO26 n/s/m validation grid and locked 3DPW test report;
- the locked temporal-smoothing validation/test report;
- the physical iPhone report generated by schema version 8;
- Core ML export reports for HMR2-S, the selected adapter, and WHAM world step;
- a manifest containing source filenames, hashes, and the selected artifacts.

The final report will distinguish three kinds of evidence:

1. **Released reference:** WHAM evaluated with its official stored inputs.
2. **Mobile accuracy:** the selected front end and smoother evaluated on the
   same labelled 3DPW population.
3. **Device workload:** the selected Core ML models executed on an iPhone 11
   Pro Max over a fixed eight-frame clip after one untimed warm-up.

It will not merge camera-relative 3DPW accuracy with world-trajectory claims,
because 3DPW supplies no synchronized phone gyroscope stream.

## Story and conclusions

The report will explain the project as a sequence of falsifiable decisions:

1. The original image path was a fallback, so connectivity had to be proven.
2. The first FastViT distillation looked plausible visually but failed direct
   and downstream evaluation.
3. Training encoder and decoder changes out of sequence made the target move;
   the project abandoned that path rather than hiding the failure.
4. Released HMR2.0-S removed the need to distill an image encoder, but its token
   was not directly compatible with WHAM's expected HMR2a space.
5. A small residual adapter recovered much of the lost accuracy without
   modifying released WHAM.
6. A validation-only YOLO26 n/s/m grid selected YOLO26m and its corresponding
   adapter before the test split was opened.
7. A validation-selected light causal smoother reduced acceleration error with
   negligible spatial regression.
8. The complete split pipeline was converted and executed on the target phone.

The conclusion will state both sides of the trade-off. On the untouched 3DPW
test population, released WHAM measured 32.67 mm PA-MPJPE, 55.58 mm MPJPE, and
65.64 mm PVE. The selected smoothed mobile pipeline measured 51.80 mm,
92.06 mm, and 107.20 mm, with acceleration error 10.72 m/s². On the iPhone 11
Pro Max it used a 243.8 MB model payload, peaked at 381.6 MB resident memory,
and achieved a median amortized latency of 187.13 ms per source frame, or about
5.34 fps.

The latency report contains one extreme YOLO stall. It inflated mean amortized
latency to 3.68 seconds per frame and the five-pass interpolated p95 to 14.18
seconds. The report will disclose this event, use the median for typical
steady-state throughput, and avoid treating a five-clip p95 as a stable tail
latency estimate. Cold model loading totaled 11.42 seconds.

## Validation

The completed refactor must pass:

- Swift unit tests for YOLO output parsing and temporal smoothing;
- a simulator Debug build;
- a signed physical-device Release build;
- a source check proving the selected seven model packages are the only models
  referenced by the production path;
- JSON schema and cross-report consistency checks;
- Markdown link and stale-terminology checks;
- `git diff --check` for files changed by the refactor.

The existing physical-device JSON remains the measured evidence. The refactor
will not silently replace, trim, or fabricate its observations.
